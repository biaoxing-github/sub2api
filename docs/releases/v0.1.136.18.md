## Detailed Changelog

Compared with `v0.1.136.17`, this release expands per-key upstream error visibility for OpenAI API-key accounts during account manual tests and scheduling-pool/account probes.

1. Record OpenAI 5xx selected-key failures on the key item
   - Modules: `backend/internal/service/account_api_key_failover.go`, `backend/internal/service/ratelimit_service.go`
   - Change: OpenAI API-key 5xx responses such as 503 now enter the selected-key cooldown path instead of being skipped by the OpenAI generic 5xx state-mutation guard.
   - User-visible impact: when an account test or gateway-selected key receives a 503, the corresponding key row shows `last_error`, `reason`, and `disabled_until` so the bad key can be removed.

2. Return manual-probe account snapshots even when the probe fails
   - Modules: `backend/internal/handler/admin/account_handler.go`, `backend/internal/handler/admin/account_handler_test.go`
   - Change: manual-probe JSON only returns HTTP 500 when no structured result exists; if the upstream call failed but produced a result, the response still includes the sanitized account DTO and `api_key_items`.
   - User-visible impact: the account page can refresh the key list and show the failed key's upstream error instead of hiding the error behind a generic failed test response.

3. Record scheduling-pool/account probe failures by key fingerprint
   - Modules: `backend/internal/service/account_probe_outcome.go`, `backend/internal/service/account_probe_test.go`
   - Change: failed probe outcomes now use the sample `KeyFingerprint` to find the matching API key and write an `api_keys_disabled` record with the upstream error body.
   - User-visible impact: scheduling-pool tests can point at the exact failing key, including 503 and other non-2xx upstream responses.

4. Broaden test/probe-only upstream error recording
   - Modules: `backend/internal/service/account_test_service.go`, `backend/internal/service/account_test_service_openai_test.go`
   - Change: account manual tests and account probes use a test/probe-specific recording rule that accepts any upstream HTTP status `>= 400`, while the production gateway 529 overload policy remains unchanged.
   - User-visible impact: less common upstream statuses, such as 529 overload or 418-style compatibility errors, still appear on the matching key row during manual diagnostics.

5. Preserve existing per-key status API surface
   - Modules: `backend/internal/service/account.go`, `backend/internal/service/ratelimit_service_401_test.go`
   - Change: `api_keys_disabled` remains the source of truth and keeps `last_error`, `reason`, `disabled_until`, and disable counts on the key fingerprint record.
   - User-visible impact: existing admin UI key rows continue to display the same fields, now populated for more upstream error classes.
